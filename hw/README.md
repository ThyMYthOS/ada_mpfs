# `hw/`

- **Purpose:** Host-side tools that talk to an Icicle Kit through OpenOCD and its serial ports.
- **License:** Apache-2.0

| File | Content |
|---|---|
| `bootmode.py` | `./x hw bootmode N [ELF] [--yes] [--dry-run] [--workdir DIR]`: switches the boot mode (0..3) with `mpfsBootmodeProgrammer.jar` of SoftConsole; see "Boot mode" below. |
| `lab.conf.example`, `lab.conf` | What differs between machines. `lab.conf.example` is in the repository and gives the default of every key; copy it to `lab.conf` (git ignores that one; `./x hw bootmode` creates it, without the header lines, when there is none) and change what differs on your machine:  the SoftConsole path (`SOFT_CONSOLE`), the OpenOCD host and port, the serial devices (`UART_PATTERN`, `{n}` is the MMUART number) and their number, and for `bootmode.py` `JAVA`, `BOOTMODE_JAR`, `FPGENPROG`, `BOOTMODE_DIE` and `BOOTMODE_PACKAGE`. `--lab FILE` or `LAB_CONF` names another one. A key that `lab.conf` does not set takes the value of `lab.conf.example`. |
| `lab.py` | Reads `lab.conf` and finds the RISC-V compiler: the version pinned in `tools/toolchain.env` (`GNAT_RISCV64_VERSION`) below `MPFS_ADA_TOOLCHAINS`; another version, or none, is an error. `run` turns a message-carrying exit into status 2. |
| `start_openocd.sh` | Starts the OpenOCD of SoftConsole (the distribution's has no `microsemi-flashpro` interface). Telnet on :4444, gdb on :3333. Runs OpenOCD as a child and ends it on Ctrl+C (see below). |
| `ocd.py` | OpenOCD telnet client and serial capture. |
| `run_image.py` | Loads an ELF onto one hart, runs it, prints the serial ports and the first trap. `--expect REGEX` sets the exit status (0 matched, 1 not matched or no output); `--expect-port N` restricts it to one port. `--uart-standin` (off by default) clocks and sets up the UARTs for an image that expects a boot stage to have done it. |
| `run_probe.py` | Runs a probe (`probe_*.S`, `trap.S` is the trap recorder `run_image.py` loads) on one hart and prints its result block; `--expect REGEX` as above. |
| `monitor.py` | Shows what the serial ports print; `--expect REGEX` as above. |
| `reset.py`, `recover.py` | `./x hw reset`: resets the board to its power-on state through OpenOCD, also after a hung debug module (`recover.py` is the sequence, shared with `svd_probe.py --recover`); see "Reset and recovery" below. |
| `svd_probe.py` | Compares the reset values of SVD registers with the board (`./x svd probe [--enable-clocks] [PERIPHERAL...]`); see below. |
| `svd_probe.list` | The rules of `svd_probe.py`: blocks it does not read by default (`skip`), registers that hold runtime state (`state`) and the registers per read command of peripherals that were never measured cleanly (`block PATTERN N reason`), and registers of which only some bits are live (`state-mask PATTERN MASK reason`: QSPIXIP.DirectAccess bits 23-16, the pin levels; CRYPTO.CONFIG bits 27-24, a fabric handshake). |

Exit status of `run_image.py`, `run_probe.py` and `monitor.py`: 0 success, 1 the expectation was not met, 2 a set-up error (no OpenOCD,
no serial port, no toolchain, bad arguments); 130 after Ctrl+C. `./x hw bootmode|openocd|run|probe|monitor|reset` is the shell around them (`tools/hw.sh`).
`tests/host/hw/run.sh` tests the scripts against a stand-in for the OpenOCD telnet port and files in place of the serial ports; the
hardware itself is not part of any automatic test.

## Ctrl+C

- `run_image.py`, `run_probe.py` and `monitor.py` end at once, also while OpenOCD does not answer (a hung bus), with one line on stderr and exit status 130. They do not clean up: after an interrupt the hart can be halted or still running the image; send `resume` or `halt` to OpenOCD (telnet :4444) or reset the board.
- `start_openocd.sh` (`./x hw openocd`) runs OpenOCD as a child and does not `exec` it. OpenOCD looks at SIGINT only between two passes of its event loop, so while it is stuck in a JTAG or abstract-command timeout it ignores Ctrl+C. On SIGINT, SIGTERM or SIGHUP (closed terminal) the script sends OpenOCD SIGTERM, waits for it for a grace period of 3 s (`START_OPENOCD_GRACE`, seconds) and then kills it with SIGKILL; a second Ctrl+C kills it at once. The exit status is 130 after Ctrl+C (143 after SIGTERM, 129 after SIGHUP), otherwise the status of OpenOCD. Only a SIGKILL of the script itself leaves OpenOCD running.
- `svd_probe.py`: see below.

## `svd_probe.py`

Reads the registers of the selected peripherals through the OpenOCD telnet port with the hart halted and compares them with `<resetValue>` under `<resetMask>`. One line per register, always `<kind>  0x<address> <PERIPHERAL.REGISTER>`; `ok`, `mismatch`, `state` and `noref` continue with ` = 0x<value>`, the value read in hex as wide as the register (`ok          0x20002008 SYSREG.CLOCK_CONFIG_CR = 0x00000010`), so a log can be compared with another run, and the kind is the prefix of the line:

| Line | Meaning |
|---|---|
| `ok` | The value matches. |
| `mismatch` | The value differs; the expected value is shown too. |
| `state` | The value differs, but the register matches a `state` rule of `svd_probe.list` (status, FIFO, message RAM, a register `--enable-clocks` wrote), or only the live bits of a `state-mask` rule differ: it only has its reset value after a reset-halt. `--compare-state` reports it as `mismatch`. |
| `noref` | Nothing to compare: the SVD has no `<resetValue>` (CLINT MTIME/MTIMECMP, the USB registers, the PLIC threshold, enable and priority registers) or `<resetMask>` is 0. |
| `unreadable` | The access failed; the text OpenOCD replied is shown. |
| `skipped` | Not read. `skipped (readAction)`: the SVD gives the register or one of its fields a `readAction`, and the read would consume data or clear status (PLIC claim/complete, UART RBR, SPI/I2C data, CAN receive RAM, USB FIFOs, ...); `--read-destructive` reads them anyway and warns. `skipped (DLAB=0)`: while `LCR.DLAB` (bit 7 of `LCR`) is 0, `DLR` (+0x80) and `DMR` (+0x84) of an MMUART are aliases of `RBR` and `IER`, and only with `DLAB=1` do they read `DLL` and `DLM`; the probe reads `LCR` first and skips them in that case. `skipped (alias of RBR/IIR)`: `THR` (+0x100) and `FCR` (+0x108) read `RBR` and `IIR`, a read of `THR` pops the receive FIFO, so they are skipped whatever `DLAB` is and count as `readAction`. `skipped (write-only)`: a register that the SVD marks `write-only` is never read, also with `--read-destructive`; it counts as `readAction`. `--read-destructive` reads all the others. (Measured with the block clocked: with `LCR=0` the offsets +0x80..+0x9C and +0x100..+0x11C read the registers at +0x00..+0x1C, +0x108 reads `IIR`; with `DLAB=1` +0x00, +0x80 and +0x100 are all `DLL`, reset value 1, and +0x84 is `DLM`, 0. With the clock off the whole block reads 0 and ignores writes.) The other lines name a block excluded by a `skip` rule, or the rest of a peripheral after an unreadable register (`--keep-going` reads on). |

By default the rules file excludes `ATHENA` (the Icicle Kit chip, MPFS250T, is not an S device: an access to the Athena block resets the OpenOCD connection), `TRACE` and `IOSCBCFG` (never measured), `ENVM` and the `*_HI` aliases (not measured separately yet). The CAN blocks (`CAN_A_LO`, `CAN_B_LO` and their `_HI` aliases) are excluded only together with `--enable-clocks` (rule kind `skip-enable-clocks`): the first access to `CAN_A_LO` after the `--enable-clocks` writes stalled the debug module at power-on, which then needed a power cycle of the board; the cause is not yet understood. Without `--enable-clocks` the block reads 0 and is probed normally. `EMMC_SD` and `DDR_CSR_APB` are the other way round (rule kind `skip-no-clocks`): while their clock is off the first access hangs the debug module, so they are excluded unless `--enable-clocks` is given. The report names the reason; `--skip-file FILE` uses another rules file, `--skip PERIPHERAL` leaves a peripheral out silently. The exclusion applies to whole-device runs (`--all` or no name): `--include PATTERN` reads a block anyway there, and a peripheral named on the command line is always read (`./x svd probe ENVM`), with a note on stderr that the block is on the default skip list and why.

A bus error in a program-buffer read can make OpenOCD drop the session. The probe then stops at once with exit status 2, names the register (or block) it accessed last and hints at the cause; it also stops after `--max-failures N` (default 3) unreadable registers in a row. `--block [PATTERN=]N` limits the registers per read command, for all peripherals or for those matching `PATTERN` (`--block 'CAN*=16'`); `--block 1` reads one register at a time and finds the register that kills the session. The rules file sets a smaller default for peripherals that were never measured cleanly (`block CAN_* 16`; also `GEM_*`, `USB`, `QSPIXIP`, `CRYPTO`): a failing access then lies within a few registers of the block that was read. Precedence: `--block PATTERN=N`, a plain `--block N`, the `block` rules, 512. At the end the hart is resumed; if the connection is gone, the probe reconnects once, and if that fails it says that the hart is still halted and exits with status 2.

Before the first read the probe checks in OpenOCD's target table (`targets`) that the selected hart is halted, also with `--no-halt`; otherwise it stops with exit status 2 and shows the table and the reply to `halt`. Harts that did not halt (`unable to halt hart 1..4` at power-on: the U54 harts) are mentioned in one `svd_probe: note:` line on stdout; reads go through the selected hart only, so they do not matter.

If more than `--identical-reads N` (default 8, 0 = never) registers of one peripheral read the same nonzero value and none of them matches its reset value, the probe prints one note after the peripheral, `svd_probe: note: <block>: <n> registers read <value>, identical reads: block probably not responding (clock/reset?)`. A block without clock or reset can answer every read with the same word: `FRQMETER` read `0xA8148A` for all 12 registers while it was gated. Registers without a reset value or with a resetMask of 0 are not counted (the PLIC priorities power up with random values, and 63 of 186 reading 7 once gave the note by chance).

`--reset-halt` sends `reset halt` to OpenOCD before the halt and the reads and prints the PC afterwards (`svd_probe: reset halt: mpfs.hart0_e51 is halted after the reset, pc=0x...`). It is not the default, because a reset destroys the state of the board, and it cannot be combined with `--no-halt`. In boot mode 0 (power-on, the hart halted by the tool, no software has run) a reset halt changes little: a run after a reset halt and a clean power-on run agreed on all `SYSREG` and `SCB_REGS` configuration registers; only the PLIC, the CLINT `MTIMECMP` registers and `MMUART0` `DLR` and `THR` differed.

`--poke ADDR=VALUE` (repeatable, executed in the order given) writes a 32-bit word with `mww` after the halt and the power-state header and before `--enable-clocks` and the reads. `ADDR` is a number or `PERIPHERAL.REGISTER` from the SVD (`--poke SYSREG.DFIAPB_CR=0x1`). A register that was poked is reported as `state` and not as `mismatch`, like the registers `--enable-clocks` writes (`--compare-state` reports it as `mismatch`). Each poke is echoed as `poke 0x... = 0x...` and the word read back follows as `readback 0x...`; neither is a register line. A write that stalls the debug module is handled like a hung read (see above); a malformed argument or an unknown register ends the run with exit status 2 before anything is sent. Like `--enable-clocks` it changes the state of the board.

### Platform state at power-on in boot mode 0

Measured on the Icicle Kit in boot mode 0, right after power-on, with the hart halted by the tool:

- `--poke SYSREG.DFIAPB_CR=0x1` (power-on value `0x2`: corner clock on, reset released) makes `CFG_DDR_SGMII_PHY` show its reset values: `CFG_DDR_SGMII_PHY.DDRPHY_MODE` reads `0x2`, where it read `0` before. Without it the block reads all zero; that comes from the gated MSS corner (`DFIAPB_CR`), not from the SVD.
- At power-on without `--enable-clocks`, `CAN_A_LO.INT_STATUS` reads 0, also after `SYSREG.DFIAPB_CR=1` and/or `SCB_REGS.MSSIO_CONTROL_CR=0x3800` (power-on value `0x7A0`). With `--enable-clocks` the first CAN access stalled the debug module (run `./x svd probe --enable-clocks --block 1 CAN_A_LO`); the cause is not known.

Before the first register line the probe prints one header line, `svd_probe: power state: DFIAPB_CR=0x... CLOCK_CONFIG_CR=0x... DEVICE_STATUS=0x... PLL_STATUS_SR=0x... MSS_RESET_CR=0x... pc=0x...`: those SYSREG registers and the PC of the selected hart (`reg pc`), read before `--enable-clocks` writes anything, so that every log documents the state the board was in. It is not a register line; scripts that parse the lines by their prefix ignore it.

`--enable-clocks` writes `SYSREG.SUBBLK_CLOCK_CR = 0xFFFFFFFF` and `SYSREG.SOFT_RESET_CR = 0`, reads both back and prints them (`svd_probe: clocks enabled: SUBBLK_CLOCK_CR=0x3FFDFFFF SOFT_RESET_CR=0x00000000`). A warning on stderr says that `SOFT_RESET_CR` is not 0 (peripherals still in reset) or that `SUBBLK_CLOCK_CR` differs from what its SVD fields allow, i.e. a clock did not come on. Bits 31, 30 and 17 of `SUBBLK_CLOCK_CR` have no field because they do not read back 1 on the MPFS250T (the usual readback is `0x3FFDFFFF`); they give no warning.

A reply such as `Timed out after 2s waiting for busy to go low (abstractcs=0x10001002)` means that the debug module is stuck busy: an access hung (the first access to `CAN_A_LO` after the `--enable-clocks` writes did). OpenOCD sends this as plain text, not as an error. The probe stops at once, whatever `--keep-going` and `--max-failures` say, and shows the reply. It makes one recovery attempt (`riscv dmi_write 0x16 0x700` clears cmderr, `riscv dmi_read 0x16` reads abstractcs; if OpenOCD does not know these commands there is no attempt). If the debug module stays busy it does **not** resume the hart (that would hang as well), names the block and the register, and asks for a power cycle of the board and a restart of OpenOCD: the debug module does not recover otherwise. If it is idle again, the register is reported as `unreadable` and the run goes on with the next peripheral.

PLIC: `PENDING0..5` have the reset value 0, but their bits follow the interrupt sources: after a power cycle `PENDING3` bit 23 (source 119, `F2M_1`, a fabric interrupt line) was set and pended again right after every completion, and `reset halt` cleared it. A rule of `svd_probe.list` reports a difference as `state`. The threshold, enable and priority registers have no reset value in the SVD (a device-specific power-up pattern, mostly repeatable across power cycles: 168 of 186 priority words and 23 of 54 enable words were identical, the thresholds were identical, and all of them were identical word for word across a `reset halt`), so they are reported as `noref` and not compared. The claim registers are skipped as `readAction`; a claim value is a function of `PENDING`, `ENABLE`, `PRIORITY` and `THRESHOLD` (verified for 123 of 123 reads) and is 0 after a `reset halt`.

When the probe stops early (hung debug module, lost connection, too many failures, a hart that is not halted, Ctrl+C) it prints, on stdout, a partial summary (`svd_probe: partial summary: N of M register(s) have a line, ...`), the last register accessed (`svd_probe: last register accessed: 0x... NAME`) and, per peripheral, the registers that were not reached (`svd_probe: not reached: P2 3, P3 1 (4 register(s))`). The cause follows on stderr and, as the last lines, on stdout, so a log made with a plain `>` shows it. The counts of the final summary keep the kinds apart: `skipped` is only what was not read after an unreadable register, `readAction` and `DLAB` are the registers that are not read by default, `excluded` are the registers of the blocks a `skip` rule left out.

Ctrl+C stops the probe at once, also when OpenOCD does not answer because the bus is hung (the read otherwise waits for `--timeout`). It prints one line, makes one attempt to resume the hart with a 2 s timeout (no retry and no new connection; none with `--no-halt`), says what it read so far and whether the hart may still be halted, and exits with status 130. A second Ctrl+C during that attempt leaves immediately. **After an interrupt the hart can remain halted**: send `resume` to OpenOCD (telnet :4444) or reset the board.

Exit status: 0 all registers `ok`, `state`, `noref` or `skipped`; 1 at least one `mismatch` or `unreadable`; 2 the probe stopped early, could not resume the hart, or the arguments or the set-up are wrong; 130 interrupted with Ctrl+C.

`tests/host/svd/probe_test.py` tests the probe against stand-ins for the telnet port that reset the connection, refuse the resume, hang or answer with errors, and that receive Ctrl+C; real hardware is not part of any automatic test.

## Reset and recovery

The probe frames every command it sends with two `echo` commands (`echo svd_probe_begin_N`, the command, `echo svd_probe_end_N`) and takes what lies between their outputs as the reply. OpenOCD prints the lines `unable to halt hart N` (with `dmcontrol` and `dmstatus`) and a prompt after each of them while a hart does not halt, so a prompt does not tell that a reply is complete, and without the framing the reply of one command was taken for the next one (`./x hw reset` then reported a value that was not there and asked for a power cycle although the board was fine).

A hung debug module (see `svd_probe.py` above: `Timed out after 2s waiting for busy to go low (abstractcs=0x10001002)`) does not need a power cycle. Measured on the Icicle Kit in boot mode 0 after `mdw 0x2010C000` had hung, this sequence in the OpenOCD console recovered the debug module and the MSS:

1. `riscv dmi_read 0x16` replied `0x10000102` (abstractcs: busy clear, cmderr=1),
2. `riscv dmi_write 0x16 0x700` (clears cmderr),
3. `reset halt`,
4. `mdw 0x20002084` (`SYSREG.SUBBLK_CLOCK_CR`) read `0x00000001`, its power-on value.

`./x hw reset` (`hw/reset.py`, host and port from `lab.conf`, `--svd FILE`, `--target T`, `--lab FILE`) runs this sequence and prints the reply of every step. It then reads `SYSREG.SUBBLK_CLOCK_CR` and `SYSREG.SOFT_RESET_CR` and compares them with the `resetValue` of the SVD. If they differ it toggles the debug module (`riscv dmi_write 0x10 0x0`, `riscv dmi_write 0x10 0x1`), sends `reset halt` again and checks again. If an OpenOCD does not know `riscv dmi_read` (an `invalid command` reply) the script says so and tries only the `reset halt`. Exit status: 0 only if the check passed (the hart is halted, the platform is in its power-on state), 2 if it failed (power-cycle the board and restart OpenOCD), if there is no OpenOCD or no merged SVD; 130 after Ctrl+C. It is also fine to run it when nothing is hung.

The reset returns the platform to its power-on state: everything that was written (`--enable-clocks`, `--poke`) is undone, and a PLL or boot state that software had set up is lost. In boot mode 0 that is the state in which the probes start anyway.

`svd_probe.py --recover` (opt-in) does this by itself: when an access stalls the debug module the probe runs the sequence, prints `hung (recovered)` for the peripheral whose access hung (its remaining registers are not read; they are counted as `hung` in the summary, and the exit status is 1), applies the `--poke` writes and `--enable-clocks` again, halts the hart again and goes on with the next peripheral. After `--max-recoveries N` (default 3) recoveries, or when the check fails, it stops with exit status 2 and without resuming the hart. Without `--recover` the probe stops at the first stall and advises `./x hw reset` (or `reset halt` in the OpenOCD console), and a power cycle if that fails. A debug module that was stuck busy is reset also if clearing `cmderr` has made it idle again: without `--recover` the register is reported as `unreadable` and the run goes on, but on the board the next accesses then failed (three `unreadable` in a row at `MMUART1_LO.IER` after the hangs of `EMMC_SD` and `DDR_CSR_APB`), so `--recover` does not trust such a module.

**Unattended use.** The only writes the probe makes to the board are the ones it is asked for: `--poke`, `--enable-clocks` and the recovery (`riscv dmi_write` to `abstractcs` and `dmcontrol`, `reset halt`). Do not poke `SCB_REGS.DEVICE_CONFIG_CR`, `SCB_REGS.RAM_SHUTDOWN_CR` or `SCB_REGS.MSS_RESET_CR`, and never read or write `THR` of an MMUART in an unattended run (a read of `DLR` or `THR` with `DLAB=0` takes receive data; the probe skips them by default). `--read-destructive` consumes data and clears status flags and does not belong in an unattended run either.

## Boot mode

`./x hw bootmode N [ELF]` (`hw/bootmode.py`, N is 0..3) runs `java -jar <SOFT_CONSOLE>/extras/mpfs/mpfsBootmodeProgrammer.jar --workdir DIR --bootmode N --die DIE --package PKG ELF`. The boot modes are as the jar describes them: 0 idle boot, 1 non-secure boot from eNVM, 2 user secure boot from sNVM, 3 factory secure boot from eNVM (`./x hw bootmode --help` says so too, and every set-up error is printed together with that help text). The jar needs a boot program ELF that is relative to its working directory: `ELF` (any directory) is copied to `DIR` (`--workdir`, default `build/bootmode`, where the jar also writes `bootmode<N>/`) and handed over by name; without `ELF` the example `bare_hello` is built (`./x build bare_hello --hart e51`) and used. Boot mode 0 (idle boot) needs no boot program: without `ELF` none is built and none is passed. `bare_hello` is linked into the L2 LIM, not for the linkage of a boot mode, so it is a stand-in until a real image is given; whether the programmer accepts it for each mode is to verify on the board. The jar ships with SoftConsole and needs `fpgenprog` from Libero; it builds a differential bitstream with `fpgenprog` and programs it through FlashPro. **The change is permanent**: it survives power cycles, is undone only by switching again or by programming another design, and rewrites the configuration of the FPGA part. The paths of java, the jar (default: below `SOFT_CONSOLE`) and `fpgenprog` and the values of `--die` and `--package` come from `lab.conf`, with the defaults of `lab.conf.example` (`JAVA`, `BOOTMODE_JAR`, `FPGENPROG`, `BOOTMODE_DIE`, `BOOTMODE_PACKAGE`). The defaults are `MPFS250T_ES` (the engineering sample, which most Icicle Kits carry; series silicon uses another die name) and `FCVG484`.

- The jar finds SoftConsole and `fpgenprog` through the environment variables `SC_INSTALL_DIR` and `FPGENPROG`; `bootmode.py` sets them from `SOFT_CONSOLE` and `FPGENPROG` of `lab.conf` (the full path of `fpgenprog`) and also puts its directory on `PATH`.
- Without `--lab`, `LAB_CONF` and `hw/lab.conf`, the command copies `hw/lab.conf.example` to `hw/lab.conf` (git ignores it) and says so; edit that file if SoftConsole, Libero or java are elsewhere.
- **Stop OpenOCD first** (`./x hw openocd`): it and the programmer both use the FlashPro. The command refuses with exit status 2 while OpenOCD answers on `OCD_HOST:OCD_PORT` of `lab.conf` (not for `--dry-run`).
- Nothing is written unless `--yes` is given or `yes` is typed at the prompt. A run without a terminal and without `--yes` refuses with exit status 2. `--dry-run` prints the command and does nothing.
- The output of the jar is shown and not interpreted. Only its exit status counts, and status 0 with no output at all is treated as a failure. The duration is printed.
- A missing java, jar or `fpgenprog` and a boot mode outside 0..3 exit with status 2 and say what to do. A jar that ends with a status other than 0, or with 0 and no output, exits with 1. A prompt answered with anything but `yes` exits with 1.
- `FPGENPROG` must be the full path of the `fpgenprog` executable, file name included (a name on `PATH` is refused); its directory is also put on `PATH` for the jar. `fpgenprog` comes with Libero SoC or the Program Debug Tool.
- The messages of the script are coloured (errors red, warnings yellow, the final success green, the rest cyan) when the output is a terminal that supports colour; `NO_COLOR` turns the colour off and `FORCE_COLOR` turns it on. The output of the jar is not touched.
- **Boot mode 0 was verified on an Icicle Kit by the project owner; the boot modes 1 to 3 have not been run on a board.** The tests (`tests/host/hw/run.sh`) use a stand-in for java and a stand-in jar that records its arguments; the options of the jar are as the project owner stated them.
- After a successful run: power-cycle the board, start OpenOCD, halt the E51 (hart 0) and read its PC. In boot mode 0 the hart waits in the boot stub (`SCB_REGS.BOOT_ROM0..7`), so the PC of a halted hart is somewhere between `0x20003120` and `0x2000312E`; the stub is decoded in `docs/lab/openocd.md`, section "The boot stub". The hart is running when it is halted, which is why the exact address varies. `./x hw reset` is for the platform state, not for this check.
