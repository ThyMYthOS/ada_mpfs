# `hw/`

- **Purpose:** Host-side tools that talk to a PolarFire SoC (MPFS) board through OpenOCD, its FlashPro and its serial ports. They are not tied to the Icicle Kit, which the defaults of `lab.conf.example` and the register values of `initialize` are those of.
- **License:** Apache-2.0

| `run_image.py` | Loads an ELF onto one hart, runs it, shows the serial ports while it runs (`--view`, `--color`; see "Serial output") and reports the first trap. `--expect REGEX` sets the exit status (0 matched, 1 not matched or no output); `--expect-port N` restricts it to one port (the console of the runtime of an image is the MMUART of its hart: port 1 for U54 hart 1, MMUART4 of hart 4 is not on the board; most examples report through `Bare_Console`, which is MMUART0 on every hart). Telnet on `OCD_PORT` (4444), gdb on :3333; `FLASHPRO_SERIAL` selects one of several FlashPro, `FLASHPRO_TYPE` (or the USB product ID) says which model it is, see `docs/lab/openocd.md`; `FLASHPRO_USB_LOCATION` names an adapter without a serial number by its USB location (`adapter usb location`); `OCD_TCK_MHZ` (lab.conf or environment) is the JTAG clock in whole MHz, given as `adapter speed` in kHz after the interface file, which sets 6000 (it prints `start_openocd: JTAG clock ...`). | `svd_probe.list` | The rules of `svd_probe.py`: blocks it does not read by default (`skip`), registers that hold runtime state (`state`) and the registers per read command of peripherals that were never measured cleanly (`block PATTERN N reason`), and registers of which only some bits are live (`state-mask PATTERN MASK reason`: QSPIXIP.DirectAccess bits 23-16, the pin levels; CRYPTO.CONFIG bits 27-24, a fabric handshake). |
| `svd_probe.py` | Compares the reset values of SVD registers with the board (`./x svd probe [--enable-clocks [--xml FILE]] [PERIPHERAL...]`); see below. |

Exit status of `run_image.py`, `run_probe.py` and `monitor.py`: 0 success, 1 the expectation was not met, 2 a set-up error (no OpenOCD,
no serial port, no toolchain, bad arguments); 130 after Ctrl+C. `./x hw bootmode|openocd|run|probe|monitor|reset|initialize` is the shell around them (`tools/hw.sh`).
`./x hw` (or `./x hw help`) prints every command with its options and the keys of `lab.conf`; `./x hw COMMAND --help` the options of one command. `tests/host/hw/run.sh` tests the scripts against a stand-in for the OpenOCD telnet port, and files and a stand-in for socat's TCP ports (`fake_uart.py`) in place of the serial ports; the live view runs on a pseudo-terminal whose screen a small emulator (`ptyrun.py`) reproduces; the
hardware itself is not part of any automatic test.

## How the tools reach the FlashPro

Every tool that programs or debugs the board goes through its FlashPro, and each one has its own way to the adapter.
That decides what a machine or a container has to provide, which tools exclude each other, and how one of several
adapters is chosen. The sources of every statement are at the end.

### The ways

| Tool | What it does with the FlashPro | How it reaches it | What it needs of the system | Choosing one of several |
|---|---|---|---|---|
| `fpgenprog` (Program Debug Tool or Libero SoC; `./x hw bootmode`) | Programs and verifies the FPGA part (`PROGRAM`, `VERIFY`) | `libfpcomm` of the tool, with `libusb` and `libcyusb` from its `lib64/` | The USB bus, `/dev/bus/usb` (inferred, see below) | The `<programmer>` element of `proj_fp.pro` (`--flashpro`, `FLASHPRO_SERIAL`); that `fpgenprog` honours it is not proven |
| `hw/*.py` (`run_image`, `run_probe`, `reset`, `initialize`, `svd_probe`, `l2_scratchpad`) | JTAG accesses to the harts and the MSS | Through OpenOCD, its telnet port (`OCD_HOST`, `OCD_PORT`); they do not open the adapter | A running OpenOCD | The OpenOCD that answers on that port |
| `hw/flashpros.py` (`./x hw flashpros`) | Lists the adapters and tells their model | The USB descriptors that the kernel has cached, in `/sys/bus/usb/devices`; no device is opened | Only that sysfs | Prints serial number (`-` if there is none), ID, name, model and USB location; the model comes from the USB product ID |
| OpenOCD, embedded FlashPro6 (`microchip-efp6`; the Icicle Kit) | JTAG, debugging, loading images | HID through `hidapi-hidraw` | `/dev/hidrawN`, readable by the user | `mchp_efp6 serial <SERIAL>` (`FLASHPRO_SERIAL`) |
| OpenOCD, FlashPro6 (`microchip-fp6`) | The same | The driver `mchp_fp6.c`; its access path was not read | Not known | `mchp_fp6 serial <SERIAL>` |
| OpenOCD, FlashPro5 and embedded FlashPro5 (`ftdi`) | The same | `libftdi1` over `libusb` | The USB bus, `/dev/bus/usb` (inferred) | `adapter serial <SERIAL>` |

The models and their USB product IDs are in `docs/lab/openocd.md`, "Several boards". Which interface file and which command for the
serial number `./x hw openocd` uses follows from the model (`FLASHPRO_TYPE` in `hw/lab.conf`, or the product ID).

The serial console is not on this path: MMUART0 to MMUART3 are the four interfaces of the CP2108 (`/dev/ttyUSB0`..`3` or
`/dev/serial/by-id/`), `hw/monitor.py` and the console of `hw/run_image.py` read them directly.

### One user of the adapter at a time

OpenOCD and `fpgenprog` cannot both have the FlashPro: `./x hw bootmode` refuses to program while something answers on
the telnet port of `lab.conf`, and a programming run needs OpenOCD stopped (`hw/bootmode.py --help`). After programming,
power-cycle the board before OpenOCD is started again. Two OpenOCD for two boards need two serial numbers, two telnet ports
and their own gdb and Tcl ports.

### What a container has to pass through

Measured on the lab machine's container on 2026-11-18, with one embedded FlashPro6 connected:

- `/dev/hidraw6` was there, `/dev/bus/usb` was not. OpenOCD with `microchip-efp6` found the adapter, examined the five harts
  and ran images; `./x hw flashpros` listed the adapter from sysfs.
- `./x hw bootmode 1 ... --yes` made the image and the bitstream, then `fpgenprog ... run_action --action PROGRAM` ended after 4.0 s
  with `Segmentation fault (core dumped)` (status 1). The boot mode was not changed: the harts were still in the boot stub
  of boot mode 0 and the hart that had been running an image in the L2 LIM had not been reset.
- That `fpgenprog` needs `/dev/bus/usb` is inferred from the libraries it ships (`libusb`, `libcyusb`) and from this crash, not shown;
  the same libraries come with Microchip's fpServer. Passing `/dev/bus/usb` through and running a
  `VERIFY` (which writes nothing) is the test.

So a machine on which all tools should work needs `/dev/hidrawN` (OpenOCD, embedded FlashPro6) and the USB bus
(`fpgenprog`, the FTDI based FlashPro5), and permission for the user to use both. The OpenOCD package has udev rules
(`contrib/60-openocd.rules`) that name the Microchip IDs `1514:2008`, `2009`, `200a` and `200b` with mode 666, group `plugdev`.

To see what a machine has: `ls /dev/hidraw* /dev/bus/usb` and `./x hw flashpros`.

## OpenOCD on another machine

`run_image.py` and `run_probe.py` give OpenOCD their images as files (`load_image FILE ADDRESS bin`), so OpenOCD must see the file.
If it runs on another machine or in another container, set `OCD_ROOT` in `lab.conf` to the path of this repository as OpenOCD sees it
(a mount of the same directory); the scripts then keep their temporary files in `build/ocd-tmp/` and name them with that prefix.
OpenOCD answers a `load_image` that failed (`couldn't open ...`) with text, not with an error status; the scripts stop with exit
status 2 and say so, instead of running whatever the memory held (measured: random LIM contents, a hart in the trap recorder).

## Serial ports

`UART_COUNT` ports are read, MMUART0 .. MMUART<count-1>. Each one is either a device of this machine or a TCP port of another machine; both can be mixed in one `lab.conf`.

| Key | Meaning |
|---|---|
| `UART<n>` | Optional, `UART0` .. `UART<count-1>`: the port of MMUART `<n>` alone, in the same two forms (`{n}` works here too). It replaces `UART_PATTERN` for that MMUART. |
| `UART_COUNT` | Number of ports (default 4). |
| `UART_BAUD`, `UART<n>_BAUD` | The baud rate at which the devices of this machine are opened: `UART_BAUD` for every port (default 115200), `UART<n>_BAUD` (for example `UART0_BAUD=230400`) for MMUART `<n>` alone. `--baud N=RATE` of `./x hw run` and `./x hw monitor` (repeatable) overrides both. A TCP port has the rate of its socat; `tests/host/hw/baud_test.py` checks the rates on a pty. |
| `UART_PATTERN` | The port of MMUART `<n>`; `{n}` is replaced by the number. A device path (a glob; the first match in sorted order is used), or `tcp:HOST:PORT` / `tcp://HOST:PORT` (`HOST` a name, an IPv4 address or `[IPv6]`). Default: the four interfaces of the CP2108 of the Icicle Kit. |

Examples (`lab.conf.example` has them with comments):

```
UART_PATTERN=tcp://lab-pc:500{n}     # MMUART0..3 on lab-pc, ports 5000..5003
UART2=tcp://lab-pc:5002              # with the default UART_PATTERN: the devices of this machine, except MMUART2
```

The syntax was chosen for three reasons. A TCP port is written where a device path is written (`UART_PATTERN`, `UART<n>`), so there is one concept and no second set of keys to keep in step with `UART_COUNT`. `{n}` is plain text substitution, so "base port + n" needs no arithmetic and no extra key: a base that ends in 0 (`500{n}` gives 5000 .. 5003) and a host per port (`tcp://uart-{n}.lab:5000`) both work. A lab whose ports do not follow a pattern, or that mixes devices and TCP, names the odd ones with `UART<n>`. `UART_PATTERN` needs no `{n}` only when every port has its `UART<n>`; a `UART<n>` outside `UART_COUNT` is an error rather than silently unused.

**The other machine.** The board is on another machine, which runs one `socat` per UART as a TCP server; the tools here connect as TCP clients:

```
socat TCP-LISTEN:5000,reuseaddr,fork FILE:/dev/serial/by-id/usb-Silicon_Labs_CP2108_...-if00-port0,b115200,raw,echo=0
```

The baud rate, 8N1 and raw mode are set by that command; the tools cannot change the baud rate of a TCP port (a device of this machine is opened at 115200 8N1 unless `UART_BAUD`, `UART<n>_BAUD` or `--baud` say another rate). `fork` lets another client connect after the first one has gone, so the tools can be run again and again against the same listener.

**Security.** `socat` TCP listeners do not authenticate or encrypt: anyone who can reach the port reads the console of the board (and, with this `socat` command, can write to it). Bind the listener to a trusted network (`TCP-LISTEN:5000,bind=10.0.0.5,...`), restrict it with a firewall (or `range=10.0.0.0/24`), or let it listen on `localhost` only and reach it through an ssh tunnel: `ssh -N -L 5000:localhost:5000 lab-pc`, with `UART0=tcp:localhost:5000` in `lab.conf`.

**Errors.** A port that cannot be opened (no such device, no permission) or connected (refused, host not found, timed out after 5 s) is a set-up error: exit status 2 and one line that names the MMUART and the endpoint, for example `serial: MMUART1: cannot connect to tcp://lab-pc:5001: Connection refused`. The TCP connections are made in parallel. During the run a TCP connection that the remote side closes or resets, and a device that disappears (USB unplugged), is reported once on stderr (`monitor.py: MMUART1: tcp://lab-pc:5001 closed the connection after 120 bytes`); the text received until then stays in the output and in what `--expect` matches, and the other ports go on. A port is not reconnected during a run.

## Serial output

`run_image.py` and `monitor.py` hand every chunk of every port to a view as it arrives (`Serial.pump`, which reads all ports with `select`), so a view can show it live; the text of a port is also kept, and `--expect` matches that.

`--view MODE`:

| Mode | Shows |
|---|---|
| `live` | One window of 8 lines per port, in which its text scrolls as it arrives; a header line over each window names the port, the endpoint and the bytes received. The default when stdout is a terminal (and `TERM` is not `dumb`). |
| `interleaved` | Complete lines in the order they arrive, each behind `MMUART<n>: ` (the prefix has its own colour per port when colours are on). A partial line is held back until its line end, or until the end of the run. The default when stdout is not a terminal (a pipe, a file, CI). |
| `blocks` | At the end of the run, one block per port that printed: a header with the byte count, then every line behind a `|` gutter (`MMUART0 (97 bytes):`, `  | TEST x: PASS`); a last line without a line end is marked `[no line end]`. |

`run_image.py` shows the serial text first, then the trap (`after:`, `first trap:`) and the `--expect` verdict; `monitor.py` ends with the verdict. After a live view the last frame stays on the screen (nothing is printed twice) and these lines follow below it.

**The live view** uses plain ANSI escape sequences, no curses. Every port of `UART_COUNT` (or the one of `--port`) has a window, also one that never prints (its header and its gutter are dim). The frame is drawn once below the cursor; afterwards only the rows that changed are rewritten, in one write with erase-to-end-of-line instead of clearing first, at most every 30 ms, so it does not flicker. The cursor is hidden while it runs and shown again when the view ends, also on Ctrl+C (the frame stays, one line `interrupted (Ctrl+C)` and exit status 130 follow below it) and on an exception. A line that is wider than the terminal is cut to its width less one column, the last visible column being `…` (`>` without UTF-8); width is the width on the screen, so East Asian wide characters count 2 and combining marks 0. A line that is still being typed (a prompt) is shown at once. A tab is expanded to 8 columns. A window has 8 lines plus its header, and one more row stays free for the cursor: four ports need 37 rows for full windows. On a shorter terminal the windows get fewer lines (4 each on 24 rows), down to 1; a terminal that cannot hold even that does not get a live view: the tool says so on stderr and uses the interleaved view. The terminal is looked at once per 50 ms; when its size changes the frame is cleared and drawn again for the new size. A port that ends (see "Serial ports") is marked `[ended]` in its header and reported below the frame at the end.

Decorations are UTF-8 box-drawing characters (`─`, `│`, `…`) when the output encoding is UTF-8, otherwise ASCII (`-`, `|`, `>`), and then a character that the output encoding lacks is escaped before its width is counted.

`--color auto|always|never` (default `auto`): `auto` is on for a terminal, unless the environment variable `NO_COLOR` is set (then off) or `FORCE_COLOR` is set (then on, also for a pipe or a file; `NO_COLOR` wins when both are set). `always` and `never` override both.

What the views do with the bytes, in every view:

- The text is decoded as UTF-8, incrementally: a multibyte character that arrives in two reads is whole. A byte that is not valid UTF-8 shows as `\xNN`, not as U+FFFD (so line noise stays visible), and so does every other control character (BEL, NUL, DEL, the C1 controls). CR LF and a lone CR end a line; a tab stays. A line of more than 4096 characters is broken there, for the display only.
- The colours of the target (`ESC [ ... m`) pass through when colours are on and are removed when they are off. They end with the line (a reset is added), so one port's colour never reaches the next line or port; a colour does not span lines.
- Every other escape sequence of the target is removed in every view, whatever `--color` says: cursor movement, erase, clear screen, OSC (titles, hyperlinks), DCS and the like, character set selection, and one that is cut off at the end. The target cannot move the cursor of your terminal or clear it.
- `--expect` matches the raw decoded text of the port (UTF-8, CR removed, the target's escape sequences still in it), so what matches does not depend on the view or the colours; to match a coloured word, match around the sequence (`ERR.*boom`).
- When the output encoding is not UTF-8 (`PYTHONIOENCODING`, a C locale), a character it cannot encode shows as `\xNN` or `\uNNNN` instead of raising an error.

A TCP port that ends during the run is reported once on stderr (see "Serial ports"), as `monitor.py: MMUART1: tcp://lab-pc:5001 closed the connection after 120 bytes`.

## Initialize

`./x hw initialize` does through OpenOCD what Microchip's first-stage boot software (HSS, the `mpfs_hal` of the platform repository: `mss_nwc_init`, `sgmii_setup`, `mss_pll_config`) does to the MSS in boot mode 0 before it switches the MSS clock: the RTC divisor for the 125 MHz reference, the SCB access timer, the dynamic enables of the PHY, the IO mux and bank set-up of the board (`--skip-io` leaves it out), the `MSSIO_CONTROL_CR` handshake, the SGMII channel set-up (reset, calibration, PLL and DLL lock; rev C silicon resets the lanes a second time) and the MSS PLL up to its lock. It does not write `ENVM_CR`, `CLOCK_CONFIG_CR` or `MSSCLKMUX`, so the CPU keeps its boot clock, and it does not touch the DDR. `--minimal` does only what `CLINT.MTIME` needs; `--dry-run` prints the steps and writes nothing. The hart is halted for the writes and resumed at the end. Run it once after a power cycle; `./x hw reset` undoes it.

**The values come from the MSS Configurator XML of the board.** The XML is required, there is no default board:

    ./x hw initialize --xml config/boards/icicle_es/ICICLE_MSS_mss_cfg.xml
    ./x hw initialize                    # MSS_XML of hw/lab.conf, a path relative to the repository root

Neither `--xml` nor `MSS_XML` is exit status 2 with `initialize: no MSS Configurator XML: give --xml FILE or set MSS_XML in hw/lab.conf ...`, also with `--dry-run`. `--xml` is relative to the working directory and comes before `MSS_XML`. The reader of the configuration generator (`config/gen/mpfs_gen/xml_reader.py`, `config/README.md`) reads the file and checks it against the merged SVD (`--svd FILE`, or else `build/svd/PolarfireSoC.svd`, made current first by `tools/svd.py ensure`); an XML it rejects is exit status 2 with its message (`FILE: GEN-Exxx PATH: message`), and nothing is written. `hw/mss_init.py` imports the reader directly, without the build tree and without a file of its own in between. What the machine needs: the repository, Python with the standard library (the reader needs nothing else), and the merged SVD. The SVD is not committed, only its hash: `tools/svd.py ensure` builds it with svdtools (`./x toolchain install svdtools`) when it is missing or stale; a machine without svdtools takes a copy of `build/svd/PolarfireSoC.svd` from another checkout of the same commit, or names one with `--svd`.

What the script keeps and what comes from the XML:

| Step | Source |
|---|---|
| Order of the steps, read-modify-writes, polls and their masks, delays, the test of the silicon revision | `hw/mss_init.py` |
| SCB access timer (`IOSCBCFG.TIMER`), `DFIAPB_CR`, `DDRPHY_STARTUP` and `DYN_CNTL`, the `MSSIO_CONTROL_CR` handshake, the soft resets and releases | `hw/mss_init.py` (no XML has them) |
| `RTC_CLOCK_CR`: the period; `ENABLE` (bit 16) is set by the second write | `mss_clocks/mss_sys/RTC_CLOCK_CR` |
| `IOMUX0_CR` to `IOMUX6_CR`, `MSSIO_BANK2/4_IO_CFG_*_CR`, `MSSIO_BANK2/4_CFG_CR` | `mss_io/io_mux` |
| `SGMII_MODE` with `REG_CDR_MOVE_STEP` (bit 22) cleared, as `mss_sgmii.c` does; `CH0_CNTL`, `CH1_CNTL`, `RECAL_CNTL`, `CLK_CNTL`, `SPARE_CNTL`, `PLL_CNTL` | `mss_sgmii/tip` |
| MSS PLL: `PLL_CTRL` (first with `REG_POWERDOWN_B` cleared, as `mss_pll.c` does), `PLL_REF_FB`, `PLL_DIV_0_1`, `PLL_DIV_2_3`, `PLL_CTRL2`, `PLL_FRACN`, `SSCG_REG_0` to `3`, `PLL_PHADJ` | `mss_clocks/mss_pll` |
| `PLL_CKMUX`, `BCLKMUX`, `FMETER_ADDR`, `FMETER_DATAW`; `CLK_XCVR` | `mss_clocks/mss_cfm`; `mss_clocks/sgmii_cfm` |

The steps are also the source of the Ada image `examples/mss_init_spike`, which sets the MSS up itself from a table that `config/gen/mss_init_table.py` makes from them (`mss_init.phases()`); `tests/host/mss_init_spike` compares the writes of that image under QEMU with this sequence.

`--dry-run` shows where each value comes from. The first line names the XML and its SHA-256, the second its design; a register with a known defect of the configurator that the sequence writes gets a note (`PLL_PHADJ`: the reader gives 0x4003, see `config/README.md`); each write of a value of the XML names its register:

    # MSS Configurator XML config/boards/icicle_es/ICICLE_MSS_mss_cfg.xml sha256 8e3f849a...
    # design ICICLE_MSS, Libero 2022.2, part MPFS250T_ES, format 0.6.5
    # note: mss_clocks/mss_pll/PLL_PHADJ: known defect of the configurator: REG_OUT3_PHSINIT = 0x8: ...
    mww 0x2000200C 0x0000007D    ;# RTC divisor (first): period 125, clock off [xml mss_clocks/mss_sys/RTC_CLOCK_CR]
    ...

A real run prints the same header before the steps, so the log names the XML too. With the XML of `config/boards/icicle_es` the sequence writes exactly the values that `hw/mss_init.py` had as literals before it read the XML (`tests/host/hw/mss_init_test.py` keeps them); the XML of `config/boards/icicle` (Libero 2024.2) differs in `IOMUX0_CR` (0xFD5) and `IOMUX4_CR` (0x88664444), a different pin assignment, which has not been run on the board.

Measured on the Icicle Kit (boot mode 0, 2026-10-23, N32): `MTIME` counts at 1.003 MHz (`probe_time.S` on hart 1: +75,221 ticks while `mcycle` counted 6,000,012 cycles at 80 MHz) after the five `--minimal` writes that follow the RTC divisor; `MSS_RESET_CR`, the SGMII soft resets, the IO set-up and the MSS PLL are not needed for that. The full sequence is the HAL's, run by hand through OpenOCD with the values of the Icicle design (the Libero MSS Configurator XML of the reference design); `PLL_PHADJ` is 0x4003 because the XML value does not fit its field. The two writes of the HAL to the GEM `nw_config` registers are left out: its header places the structure at 0x20110004, so the write lands on the read-only status register at 0x20110008.

## Ctrl+C

- `run_image.py`, `run_probe.py` and `monitor.py` end at once, also while OpenOCD does not answer (a hung bus), with one line on stderr and exit status 130 (a live view of the serial ports shows the cursor again first and leaves its last frame on the screen). They do not clean up: after an interrupt the hart can be halted or still running the image; send `resume` or `halt` to OpenOCD (telnet :4444) or reset the board.
- `start_openocd.sh` (`./x hw openocd`) runs OpenOCD as a child and does not `exec` it. OpenOCD looks at SIGINT only between two passes of its event loop, so while it is stuck in a JTAG or abstract-command timeout it ignores Ctrl+C. On SIGINT, SIGTERM or SIGHUP (closed terminal) the script sends OpenOCD SIGTERM, waits for it for a grace period of 3 s (`START_OPENOCD_GRACE`, seconds) and then kills it with SIGKILL; a second Ctrl+C kills it at once. The exit status is 130 after Ctrl+C (143 after SIGTERM, 129 after SIGHUP), otherwise the status of OpenOCD. Only a SIGKILL of the script itself leaves OpenOCD running.
- `svd_probe.py`: see below.

## `svd_probe.py`

Reads the registers of the selected peripherals through the OpenOCD telnet port with the hart halted and compares them with `<resetValue>` under `<resetMask>`. One line per register, always `<kind>  0x<address> <PERIPHERAL.REGISTER>`; `ok`, `mismatch`, `state` and `noref` continue with ` = 0x<value>`, the value read in hex as wide as the register (`ok          0x20002008 SYSREG.CLOCK_CONFIG_CR = 0x00000010`), so a log can be compared with another run, and the kind is the prefix of the line:

| Line | Meaning |
|---|---|
| `ok` | The value matches. |
| `mismatch` | The value differs; the expected value is shown too. |
| `state` | The value differs, but the register matches a `state` rule of `svd_probe.list` (status, FIFO, message RAM, a register `--enable-clocks` wrote), or only the live bits of a `state-mask` rule differ: it only has its reset value after a reset-halt. `--compare-state` reports it as `mismatch`. |
| `noref` | Nothing to compare: the SVD has no `<resetValue>` (CLINT MTIME/MTIMECMP, the USB registers that were not measured, the PLIC threshold, enable and priority registers) or `<resetMask>` is 0. |
| `unreadable` | The access failed; the text OpenOCD replied is shown. |
| `skipped` | Not read. `skipped (readAction)`: the SVD gives the register or one of its fields a `readAction`, and the read would consume data or clear status (PLIC claim/complete, UART RBR, SPI/I2C data, CAN receive RAM, USB FIFOs, ...); `--read-destructive` reads them anyway and warns. `skipped (DLAB=0)`: while `LCR.DLAB` (bit 7 of `LCR`) is 0, `DLR` (+0x80) and `DMR` (+0x84) of an MMUART are aliases of `RBR` and `IER`, and only with `DLAB=1` do they read `DLL` and `DLM`; the probe reads `LCR` first and skips them in that case. `skipped (alias of RBR/IIR)`: `THR` (+0x100) and `FCR` (+0x108) read `RBR` and `IIR`, a read of `THR` pops the receive FIFO, so they are skipped whatever `DLAB` is and count as `readAction`. `skipped (write-only)`: a register that the SVD marks `write-only` is never read, also with `--read-destructive`; it counts as `readAction`. `--read-destructive` reads all the others. (Measured with the block clocked: with `LCR=0` the offsets +0x80..+0x9C and +0x100..+0x11C read the registers at +0x00..+0x1C, +0x108 reads `IIR`; with `DLAB=1` +0x00, +0x80 and +0x100 are all `DLL`, reset value 1, and +0x84 is `DLM`, 0. With the clock off the whole block reads 0 and ignores writes.) The other lines name a block excluded by a `skip` rule, or the rest of a peripheral after an unreadable register (`--keep-going` reads on). |

By default the rules file excludes `ATHENA` (the Icicle Kit chip, MPFS250T, is not an S device: an access to the Athena block resets the OpenOCD connection), `TRACE` and `IOSCBCFG` (never measured), `ENVM` and the `*_HI` aliases (not measured separately yet). The CAN blocks (`CAN_A_LO`, `CAN_B_LO` and their `_HI` aliases) are excluded only together with `--enable-clocks` (rule kind `skip-enable-clocks`): the first access to `CAN_A_LO` after the `--enable-clocks` writes stalled the debug module at power-on, which then needed a power cycle of the board; the cause is not yet understood. Without `--enable-clocks` the block reads 0 and is probed normally. `EMMC_SD` and `DDR_CSR_APB` are the other way round (rule kind `skip-no-clocks`): while their clock is off the first access hangs the debug module, so they are excluded unless `--enable-clocks` is given. The report names the reason; `--skip-file FILE` uses another rules file, `--skip PERIPHERAL` leaves a peripheral out silently. The exclusion applies to whole-device runs (`--all` or no name): `--include PATTERN` reads a block anyway there, and a peripheral named on the command line is always read (`./x svd probe ENVM`), with a note on stderr that the block is on the default skip list and why.

A bus error in a program-buffer read can make OpenOCD drop the session. The probe then stops at once with exit status 2, names the register (or block) it accessed last and hints at the cause; it also stops after `--max-failures N` (default 3) unreadable registers in a row. `--block [PATTERN=]N` limits the registers per read command, for all peripherals or for those matching `PATTERN` (`--block 'CAN*=16'`); `--block 1` reads one register at a time and finds the register that kills the session. The rules file sets a smaller default for peripherals that were never measured cleanly (`block CAN_* 16`; also `GEM_*`, `USB`, `QSPIXIP`, `CRYPTO`): a failing access then lies within a few registers of the block that was read. Precedence: `--block PATTERN=N`, a plain `--block N`, the `block` rules, 512. At the end the hart is resumed; if the connection is gone, the probe reconnects once, and if that fails it says that the hart is still halted and exits with status 2.

Before the first read the probe checks in OpenOCD's target table (`targets`) that the selected hart is halted, also with `--no-halt`; otherwise it stops with exit status 2 and shows the table and the reply to `halt`. Harts that did not halt (`unable to halt hart 1..4` at power-on: the U54 harts) are mentioned in one `svd_probe: note:` line on stdout; reads go through the selected hart only, so they do not matter.

If more than `--identical-reads N` (default 8, 0 = never) registers of one peripheral read the same nonzero value and none of them matches its reset value, the probe prints one note after the peripheral, `svd_probe: note: <block>: <n> registers read <value>, identical reads: block probably not responding (clock/reset?)`. A block without clock or reset can answer every read with the same word: `FRQMETER` read `0xA8148A` for all 12 registers while it was gated. Registers without a reset value or with a resetMask of 0 are not counted (the PLIC priorities power up with random values, and 63 of 186 reading 7 once gave the note by chance).

`--reset-halt` sends `reset halt` to OpenOCD before the halt and the reads and prints the PC afterwards (`svd_probe: reset halt: mpfs.hart0_e51 is halted after the reset, pc=0x...`). It is not the default, because a reset destroys the state of the board, and it cannot be combined with `--no-halt`. In boot mode 0 (power-on, the hart halted by the tool, no software has run) a reset halt changes little: a run after a reset halt and a clean power-on run agreed on all `SYSREG` and `SCB_REGS` configuration registers; only the PLIC, the CLINT `MTIMECMP` registers and `MMUART0` `DLR` and `THR` differed.

`--poke ADDR=VALUE` (repeatable, executed in the order given) writes a 32-bit word with `mww` after the halt and the power-state header and before `--enable-clocks` and the reads. `ADDR` is a number or `PERIPHERAL.REGISTER` from the SVD (`--poke SYSREG.DFIAPB_CR=0x1`). A register that was poked is reported as `state` and not as `mismatch`, like the registers `--enable-clocks` writes (`--compare-state` reports it as `mismatch`). Each poke is echoed as `poke 0x... = 0x...` and the word read back follows as `readback 0x...`; neither is a register line. A write that stalls the debug module is handled like a hung read (see above); a malformed argument or an unknown register ends the run with exit status 2 before anything is sent. Like `--enable-clocks` it changes the state of the board.

### Platform state at power-on in boot mode 0

Measured on the Icicle Kit in boot mode 0, right after power-on, with the hart halted by the tool:

- `--poke SYSREG.DFIAPB_CR=0x1` (power-on value `0x2`: corner clock on, reset released) makes `CFG_DDR_SGMII_PHY` show its reset values: `CFG_DDR_SGMII_PHY.DDRPHY_MODE` reads `0x2`, where it read `0` before. Without it the block reads all zero; that comes from the gated MSS corner (`DFIAPB_CR`), not from the SVD.
- At power-on without `--enable-clocks`, `CAN_A_LO.INT_STATUS` reads 0, also after `SYSREG.DFIAPB_CR=1` and/or `SCB_REGS.MSSIO_CONTROL_CR=0x3800` (power-on value `0x7A0`). With `--enable-clocks` the first CAN access stalled the debug module (run `./x svd probe --enable-clocks --block 1 CAN_A_LO`); the cause is not known.

Before the first register line the probe prints one header line, `svd_probe: power state: DFIAPB_CR=0x... CLOCK_CONFIG_CR=0x... DEVICE_STATUS=0x... PLL_STATUS_SR=0x... MSS_RESET_CR=0x... pc=0x...`: those SYSREG registers and the PC of the selected hart (`reg pc`), read before `--enable-clocks` writes anything, so that every log documents the state the board was in. It is not a register line; scripts that parse the lines by their prefix ignore it.

`--enable-clocks` writes `SYSREG.SUBBLK_CLOCK_CR = 0xFFFFFFFF` and `SYSREG.SOFT_RESET_CR = 0`, reads both back and prints them (`svd_probe: clocks enabled: SUBBLK_CLOCK_CR=0x3FFDFFFF SOFT_RESET_CR=0x00000000`). A warning on stderr says that `SOFT_RESET_CR` is not 0 (peripherals still in reset) or that `SUBBLK_CLOCK_CR` differs from what its SVD fields allow, i.e. a clock did not come on. Bits 31, 30 and 17 of `SUBBLK_CLOCK_CR` have no field because they do not read back 1 on the MPFS250T (the usual readback is `0x3FFDFFFF`); they give no warning. It then sets up the reference clock that `CLINT.MTIME` needs (`mss_init.refclk`, six writes: `SYSREG.RTC_CLOCK_CR` with the period of the XML, 125 on the Icicle Kit, `IOSCBCFG.TIMER`, `SYSREG.DFIAPB_CR` = 1, `SCB_REGS.MSSIO_CONTROL_CR` = 0x3800, `CFG_DDR_SGMII_PHY.CLK_CNTL` of the XML, 0xF00050CC) and prints `svd_probe: reference clock set up` with the XML and its SHA-256. The values come from the MSS Configurator XML of the board as for `./x hw initialize`: `--xml FILE`, or else `MSS_XML` of the lab configuration (`--lab FILE`, `LAB_CONF` or `hw/lab.conf`), read against `--svd`; without one, or with one the reader rejects, the probe exits with 2 before it connects (`--list` needs none); as a side effect the `CFG_DDR_SGMII_PHY` block reads its registers (at power-on every PHY register reads 0), and the five registers just named are `state` with `--enable-clocks`.

A reply such as `Timed out after 2s waiting for busy to go low (abstractcs=0x10001002)` means that the debug module is stuck busy: an access hung (the first access to `CAN_A_LO` after the `--enable-clocks` writes did). OpenOCD sends this as plain text, not as an error. The probe stops at once, whatever `--keep-going` and `--max-failures` say, and shows the reply. It makes one recovery attempt (`riscv dmi_write 0x16 0x700` clears cmderr, `riscv dmi_read 0x16` reads abstractcs; if OpenOCD does not know these commands there is no attempt). If the debug module stays busy it does **not** resume the hart (that would hang as well), names the block and the register, and asks for a power cycle of the board and a restart of OpenOCD: the debug module does not recover otherwise. If it is idle again, the register is reported as `unreadable` and the run goes on with the next peripheral.

PLIC: `PENDING0..5` have the reset value 0, but their bits follow the interrupt sources: after a power cycle `PENDING3` bit 23 (source 119, `F2M_1`, a fabric interrupt line) was set and pended again right after every completion, and `reset halt` cleared it. A rule of `svd_probe.list` reports a difference as `state`. The threshold, enable and priority registers have no reset value in the SVD (a device-specific power-up pattern, mostly repeatable across power cycles: 168 of 186 priority words and 23 of 54 enable words were identical, the thresholds were identical, and all of them were identical word for word across a `reset halt`), so they are reported as `noref` and not compared. The claim registers are skipped as `readAction`; a claim value is a function of `PENDING`, `ENABLE`, `PRIORITY` and `THRESHOLD` (verified for 123 of 123 reads) and is 0 after a `reset halt`.

When the probe stops early (hung debug module, lost connection, too many failures, a hart that is not halted, Ctrl+C) it prints, on stdout, a partial summary (`svd_probe: partial summary: N of M register(s) have a line, ...`), the last register accessed (`svd_probe: last register accessed: 0x... NAME`) and, per peripheral, the registers that were not reached (`svd_probe: not reached: P2 3, P3 1 (4 register(s))`). The cause follows on stderr and, as the last lines, on stdout, so a log made with a plain `>` shows it. The counts of the final summary keep the kinds apart: `skipped` is only what was not read after an unreadable register, `readAction` and `DLAB` are the registers that are not read by default, `excluded` are the registers of the blocks a `skip` rule left out.

Ctrl+C stops the probe at once, also when OpenOCD does not answer because the bus is hung (the read otherwise waits for `--timeout`). It prints one line, makes one attempt to resume the hart with a 2 s timeout (no retry and no new connection; none with `--no-halt`), says what it read so far and whether the hart may still be halted, and exits with status 130. A second Ctrl+C during that attempt leaves immediately. **After an interrupt the hart can remain halted**: send `resume` to OpenOCD (telnet :4444) or reset the board.

Exit status: 0 all registers `ok`, `state`, `noref` or `skipped`; 1 at least one `mismatch` or `unreadable`; 2 the probe stopped early, could not resume the hart, or the arguments or the set-up are wrong; 130 interrupted with Ctrl+C.

`tests/host/svd/probe_test.py` tests the probe against stand-ins for the telnet port that reset the connection, refuse the resume, hang or answer with errors, and that receive Ctrl+C; real hardware is not part of any automatic test.

## Reset and recovery

The probe frames every command it sends with two `echo` commands (`echo svd_probe_begin_N`, the command, `echo svd_probe_end_N`) and takes what lies between their outputs as the reply. OpenOCD prints the lines `unable to halt hart N` (with `dmcontrol` and `dmstatus`) and a prompt after each of them while a hart does not halt, so a prompt does not tell that a reply is complete, and without the framing the reply of one command was taken for the next one (`./x hw reset` then reported a value that was not there and asked for a power cycle although the board was fine).

A hung debug module (see `svd_probe.py` above: `Timed out after 2s waiting for busy to go low (abstractcs=0x10001002)`) does not need a power cycle. Measured on the Icicle Kit in boot mode 0 after `mdw 0x2010C000` had hung, this sequence in the OpenOCD console recovered the debug module and the MSS:

1. `riscv dmi_read 0x16` replied `0x10000102` (abstractcs: busy clear, cmderr=1),
2. `riscv dmi_write 0x16 0x700` (clears cmderr),
3. `reset halt`,
4. `mdw 0x20002084` (`SYSREG.SUBBLK_CLOCK_CR`) read `0x00000001`, its power-on value.

`./x hw reset` (`hw/reset.py`, host and port from `lab.conf`, `--svd FILE`, `--target T`, `--lab FILE`) runs this sequence and prints the reply of every step. It then reads `SYSREG.SUBBLK_CLOCK_CR` and `SYSREG.SOFT_RESET_CR` and compares them with the `resetValue` of the SVD. If they differ it toggles the debug module (`riscv dmi_write 0x10 0x0`, `riscv dmi_write 0x10 0x1`), sends `reset halt` again and checks again. If an OpenOCD does not know `riscv dmi_read` (an `invalid command` reply) the script says so and tries only the `reset halt`. Exit status: 0 only if the check passed (the hart is halted, the platform is in its power-on state), 2 if it failed (power-cycle the board and restart OpenOCD), if there is no OpenOCD or no merged SVD; 130 after Ctrl+C. It is also fine to run it when nothing is hung.

After the check `./x hw reset` clears what a `reset halt` leaves behind (`hw/hart_state.py`): the PLIC enables of the nine contexts and `fcsr` of the four U54 (the harts are halted); `./x hw initialize` does the same. It exits with 2 if an `fcsr` could not be written.

The reset returns the platform to its power-on state: everything that was written (`--enable-clocks`, `--poke`) is undone, and a PLL or boot state that software had set up is lost. In boot mode 0 that is the state in which the probes start anyway.

`svd_probe.py --recover` (opt-in) does this by itself: when an access stalls the debug module the probe runs the sequence, prints `hung (recovered)` for the peripheral whose access hung (its remaining registers are not read; they are counted as `hung` in the summary, and the exit status is 1), applies the `--poke` writes and `--enable-clocks` again, halts the hart again and goes on with the next peripheral. After `--max-recoveries N` (default 3) recoveries, or when the check fails, it stops with exit status 2 and without resuming the hart. Without `--recover` the probe stops at the first stall and advises `./x hw reset` (or `reset halt` in the OpenOCD console), and a power cycle if that fails. A debug module that was stuck busy is reset also if clearing `cmderr` has made it idle again: without `--recover` the register is reported as `unreadable` and the run goes on, but on the board the next accesses then failed (three `unreadable` in a row at `MMUART1_LO.IER` after the hangs of `EMMC_SD` and `DDR_CSR_APB`), so `--recover` does not trust such a module.

**Unattended use.** The only writes the probe makes to the board are the ones it is asked for: `--poke`, `--enable-clocks` and the recovery (`riscv dmi_write` to `abstractcs` and `dmcontrol`, `reset halt`). Do not poke `SCB_REGS.DEVICE_CONFIG_CR`, `SCB_REGS.RAM_SHUTDOWN_CR` or `SCB_REGS.MSS_RESET_CR`, and never read or write `THR` of an MMUART in an unattended run (a read of `DLR` or `THR` with `DLAB=0` takes receive data; the probe skips them by default). `--read-destructive` consumes data and clears status flags and does not belong in an unattended run either.

## Boot mode

`./x hw bootmode N [ELF]` (`hw/bootmode.py`, N is 0..3) switches the boot mode of the board. It is a Python port (`hw/bootprog.py`) of the Java `mpfsBootmodeProgrammer` of Microchip: it needs neither Java nor the jar, only `fpgenprog` from Libero SoC or the Program Debug Tool. It makes the image of the boot mode from the boot program `ELF`, builds an `fpgenprog` project with it (the boot mode, an eNVM or sNVM client), lets `fpgenprog` generate the differential bitstream and programs it through FlashPro. The boot modes are as the Java tool describes them: 0 idle boot, 1 non-secure boot from eNVM, 2 user secure boot from sNVM, 3 factory secure boot from eNVM (`./x hw bootmode --help` says so too, and every set-up error is printed together with that help text).

**The change is permanent**: it survives power cycles, is undone only by switching again or by programming another design, and rewrites the configuration of the FPGA part. What differs between the boot modes:

| Boot mode | Image | Boot program linked for |
|---|---|---|
| 0 | none: a client of one byte (`:0100000000FF`) | none, no ELF |
| 1 | a header page (a jump to the next page, the length, the boot vectors, `BOOT MODE 1 DUMMY SBIC`) in front of the image, in eNVM | eNVM page 1 or higher (`0x20220100`, ...) |
| 2 | a header of 60 bytes (address, length in words, boot vectors, SHA-256) in front of the image, in sNVM, from `--snvm-page` on; `--usk` is the key, `--encrypt` stores authenticated ciphertext | the LIM (`0x08000000` ... `0x081DFFFF`), 32-bit aligned, a multiple of 4 bytes |
| 3 | a certificate (SBIC: addresses, length, boot vectors, SHA-384 of the image, DER ECDSA signature, 208 bytes) and zeros up to the next page in front of the image, in eNVM; the public key is in the boot mode | eNVM page 1 or higher |

- **The ELF** is a file of any directory (the Java tool wants it below its working directory; this one does not copy it). Without `ELF` the example `bare_hello` is built (`./x build bare_hello --hart e51`) and used; it is linked into the L2 LIM, not for the linkage of a boot mode, so it is a stand-in until a real image is given (modes 1 and 3 refuse it with the address they need). Boot mode 0 needs no boot program: an `ELF` that is given is ignored with a warning.
- **The work** is in `DIR` (`--workdir`, default `build/bootmode`), in `bootmode<N>/`, which is made new for every run: the images (`<elf>-bm<N>-...bin` and `.hex`), the project `fpgenprogProject/`, `debugLog.txt`, the USK (`<elf>-bm2-usk.txt`) and the public key (`<elf>-bm3-public-key-xy.txt`). The image and the bitstream are made first; only then the prompt comes (`--prepare-only` stops there: no prompt, no FlashPro, and OpenOCD may run).
- **Boot mode 2:** `--usk` is 12 bytes as 24 hex digits (`0x` in front is allowed); `0` or none gives a random one, which is printed and saved next to the image (without it the stored image cannot be read). The USK is a command-line argument of `fpgenprog` and so visible to other users of the machine. `--snvm-page` (alias `--snvm_page`) is 0..220; the image with its header must fit the sNVM from there.
- **Boot mode 3:** `--keys PRIVATE.pem PUBLIC.pem` gives the ECDSA key pair of NIST P-384 (PKCS#8 without a password, and X.509; the public key must belong to the private one). Without `--keys` a pair is generated and **the private key is not saved**: only this run can sign, so keep a key if you will build the image again. Keys with OpenSSL: `openssl ecparam -name secp384r1 -genkey -noout -out combined.ec.key`, `openssl pkcs8 -topk8 -nocrypt -in combined.ec.key -out private.pem`, `openssl ec -in private.pem -pubout -out public.pem`. The signature needs the Python package `cryptography` (`tools/requirements.txt`; `./x toolchain install`).
- **Tools:** `fpgenprog` (full path, file name included, a name on `PATH` is refused; `FPGENPROG` of `lab.conf`), `riscv64-elf-objcopy` and `riscv64-elf-readelf` of the pinned GNAT cross toolchain (`lab.py`, `tools/toolchain.env`). The die and the package come from `BOOTMODE_DIE` and `BOOTMODE_PACKAGE` of `lab.conf` or from `--die` and `--package`; the defaults are `MPFS250T_ES` (the engineering sample, which most Icicle Kits carry; series silicon uses another die name) and `FCVG484`.
- **More than one FlashPro:** `--flashpro ID` (or `FLASHPRO_ID` in `lab.conf`; for a FlashPro5 that `FLASHPRO_SERIAL` names `S2` and the serial number, an assumption; else `FLASHPRO_SERIAL` as it is) names the one to use: the name that the programming tools of Microchip give it, which `./x hw program --scan` lists with the model. It is not in general the USB serial number that `./x hw flashpros` shows, and a FlashPro whose USB descriptor has no serial number (`-` there) has only this name. The Java tool has no such option (its source says `TODO: Allow to select one flashpro from many connected`) and leaves the choice to `fpgenprog`, which cannot make it: `fpgenprog run_action` takes only `--location` and `--action`, the programmer that the project file names is not used, and its Tcl script calls `run_selected_actions` without `-name`, which runs the action on every connected programmer (the Libero SoC Tcl command reference says so). Seen with an embedded FlashPro6 and a FlashPro5 connected: both did `PROGRAM`, and the FlashPro5 failed (`Instruction timed out`, status 1). So `bootmode` asks FlashPro Express (`FPEXPRESS`, or the `FPExpress` next to `fpgenprog`) which programmers are connected. With one and none named, that one is taken and `fpgenprog` programs as before. With more than one, and none named or a name FlashPro Express does not list, it stops before anything runs (exit status 2) and lists them; with a name it makes the image and the bitstream with `fpgenprog` and then programs the `proj_fp/target.ppd` that `fpgenprog` leaves in the project through `hw/program.py`, which gives the programmer to `run_selected_actions -name`. **That route has not been run on a board with two FlashPros.** After a run the programmers that its output names are printed; if `fpgenprog` ran the check before the programming (a verify, which writes nothing) on a programmer other than the named one, nothing is programmed (exit status 1). Without FlashPro Express none of this is done: a name is written into the project as a minimal element, which `fpgenprog` does not honour with several connected, and the check above refuses. `./x hw flashpros` lists the serial numbers of the connected FlashPro adapters (from the USB descriptors in sysfs, vendor 1514; that `fpgenprog` names its programmer by the same serial is not proven). After every run the FlashPro that was used is printed.
- Without `--lab`, `LAB_CONF` and `hw/lab.conf`, the command copies `hw/lab.conf.example` to `hw/lab.conf` (git ignores it) and says so; edit that file if Libero is elsewhere.
- **Stop OpenOCD first** (`./x hw openocd`): it and the programmer both use the FlashPro. The command refuses with exit status 2 while OpenOCD answers on `OCD_HOST:OCD_PORT` of `lab.conf` (not for `--dry-run` and `--prepare-only`).
- Nothing is written to the board unless `--yes` is given or `yes` is typed at the prompt. A run without a terminal and without `--yes` refuses with exit status 2. `--dry-run` says what it would do and does nothing (it is not the `--dryrun` of the Java tool, which prepares everything and stops before the programming: that is `--prepare-only`).
- The output of `fpgenprog` is shown. A step that ends with a status other than 0 stops the run (exit status 1, with the message of the step and `debugLog.txt`), and so does a PROGRAM that ends with status 0 and prints nothing. The duration is printed.
- A missing `fpgenprog` or toolchain, a boot mode outside 0..3, an option that does not fit the boot mode (`--usk`, `--snvm-page` and `--encrypt` only for 2, `--keys` only for 3) and a missing ELF exit with status 2 and say what to do. A prompt answered with anything but `yes` exits with 1.
- The messages of the script are coloured (errors red, warnings yellow, the final success green, the rest cyan) when the output is a terminal that supports colour; `NO_COLOR` turns the colour off and `FORCE_COLOR` turns it on. The output of `fpgenprog` is not touched.
- **What differs from the Java tool:** no Java; the ELF may be anywhere; `--keys` does not turn on `--verify` (the Java tool does, by a `break` that is missing in its argument parser); the public key must belong to the private key; the generated private key is reported as not saved; a FlashPro can be chosen. Everything else is the same: the images, the certificate (but for the signature, which ECDSA randomises) and the arguments of every `fpgenprog` call are identical to those of the Java tool for the same boot program, which `tests/host/hw/bootprog_test.py` checks against the SHA-256 and the argument lines that the Java tool made.
- **Boot mode 0 was verified on an Icicle Kit by the project owner; the boot modes 1 to 3 have not been run on a board**, with this tool or with the jar. The tests (`tests/host/hw/run.sh`, `bootprog_test.py`) use a stand-in for `fpgenprog` (`fake_fpgenprog.py`, which records its calls and makes the project folder); the real `fpgenprog` was run up to the bitstream (no programming) on the boot programs of the tests, and what it made was compared with the Java tool's. What the tests cannot show: that `fpgenprog` programs what it is given, and that it honours a FlashPro in the project file.
- After a successful run: power-cycle the board, start OpenOCD, halt the E51 (hart 0) and read its PC. In boot mode 0 the hart waits in the boot stub (`SCB_REGS.BOOT_ROM0..7`), so the PC of a halted hart is somewhere between `0x20003120` and `0x2000312E`; the stub is decoded in `docs/lab/openocd.md`, section "The boot stub". The hart is running when it is halted, which is why the exact address varies. `./x hw reset` is for the platform state, not for this check.

## Programming the FPGA

`./x hw program FILE` (`hw/program.py`) programs the FPGA from a STAPL (`.stp`) or PPD (`.ppd`) file with FlashPro Express, the files that Libero SoC exports; it replaces a shell script that ran `FPExpress` on a generated Tcl file. Where `./x hw bootmode` builds an image and a bitstream from a boot program, this takes the bitstream of a design as it is. It runs `FPExpress script:<workdir>/program.tcl`, and the script (job project for the programmer, the TCK frequency if one is set, `scan_chain_prg`, `enable_device`, `set_programming_file`, `set_programming_action`, `run_selected_actions`) is written to `<workdir>` (default `build/program`) next to the other Tcl files and `program.log`, so what ran can be read afterwards. `--dry-run` prints the scripts and starts nothing.

- **FPExpress:** `FPEXPRESS` in `lab.conf` (full path, file name included); empty, it is the `FPExpress` in the directory of `FPGENPROG`, where the Program Debug Tool and Libero SoC keep it.
- **Programmer:** `--programmer ID`, else `FLASHPRO_ID` of `lab.conf`, else FlashPro Express is run once with an empty programmer name and prints the programmers it sees. The name is the one in quotes: `programmer 'B347B62F' : Embedded FlashPro6` (the line before it, `Programmer: Embedded FP6 'B347B62F' : Version = EF9B`, names it the same way); the text after the name is the model. This is **not** in general the serial number of OpenOCD and of `./x hw flashpros`: on one FlashPro5 FlashPro Express said `S200BM0VJ` where OpenOCD showed `00BM80VJ`. For a FlashPro5 that `FLASHPRO_SERIAL` names (`FLASHPRO_TYPE` `fp5` or `efp5`, or the USB descriptors of that serial number say so) the programmer is therefore **assumed** to be `S2` and the serial number (not again if it starts with `S2`), as a default only: a run looks for the programmers and stops with a message that says how the name was derived if it is not among them (the one pair seen differs by one character after the prefix, so this may need a better rule). For an embedded FlashPro6 no rule is known (`B347B62F` is how FlashPro Express named one), so FlashPro Express finds it. `--scan` does not use the guess. More than one programmer found is an error that lists them.
- **Device:** `--device NAME`, else the `Part:` of the line the scan of the chain prints: `programmer 'B347B62F' : Device 1: F81A1CF Mfr: Microsemi Part: MPFS250(T_ES|TS_ES)`. The name goes into the Tcl script as the scan printed it, with the parentheses and the bar. (Splitting it into `MPFS250T_ES` and `MPFS250TS_ES`, which the JTAG target is said to take and which the job project of the Icicle Kit design uses, was tried and taken out again: it did not work as hoped on the board.) None or more than one device found is an error that lists what was found.
- **`--scan`:** no `FILE`; it lists the programmers FlashPro Express finds, with their models, and the devices of each JTAG chain (number, part as the scan prints it, IDCODE, manufacturer), or of the one named with `--programmer`. It only reads: no prompt, no `--yes`, nothing is written. Exit status 0 if every chain scanned shows a device, 1 if one does not (the last lines of its output are printed), 2 for a set-up error.
- **`--action`:** the action of FlashPro Express, `PROGRAM` by default. Its manual lists `DEVICE_INFO`, `ENC_DATA_AUTHENTICATION`, `ERASE`, `PROGRAM`, `READ_IDCODE` and `VERIFY`; any name is passed through, and FlashPro Express rejects one that does not exist. `DEVICE_INFO`, `READ_IDCODE` and `VERIFY` only read: no prompt and no `--yes`. All of them still need a `FILE`: FlashPro Express stops with `A programming file must be loaded before running the command 'set_programming_action'` without one (seen with `DEVICE_INFO` on a board, as the manual of `set_programming_action` says); the file is loaded, not written.
- **TCK frequency:** `--tck MHZ`, else `TCK_MHZ` of `lab.conf`, else FlashPro Express decides (4 MHz by default, or the frequency of the programming file, says its manual). `OCD_TCK_MHZ` is not used here: it is the clock of `./x hw openocd` (see `start_openocd.sh`), and the highest clock that works is not the same for OpenOCD and for FlashPro Express (OpenOCD went up to 9 MHz on one setup, programming up to 15 MHz). `MHZ` is a whole number: FlashPro Express takes the frequency in Hz in steps of 1 MHz, and for a FlashPro6 only 1 to 20 MHz (on a board it rejected `10` with `expecting 1000000, 2000000, ... or 20000000`, although its manual says MHz), so `--tck 10` becomes `-freq {10000000}`. A frequency is put into the scan and programming scripts as `configure_flashpro6_prg -force_freq {ON} -freq {HZ}` (`configure_flashpro5_prg` for a FlashPro5, whose steps are not known and are left to FlashPro Express; another model is an error), so FlashPro Express uses exactly that clock and not the one of the programming file: the clock that is set is the clock that is used. The model comes from the programmer line, so a run with a frequency looks for the programmers even when one is named, and checks that it is there.
- **Permanent:** `PROGRAM` and `ERASE` change the FPGA, so nothing is written without `--yes` or a typed `yes`; without `--yes` and without a terminal the script refuses (exit status 2). OpenOCD and FlashPro Express both use the FlashPro, so the script refuses while OpenOCD answers on the port of `lab.conf`.
- **FlashPro Express 2026.1:** a `scan_chain_prg` right after `auto_construct_job_project` failed (with a FlashPro5 and with a FlashPro6; whether the fault is in FlashPro Express or in its installation is not known). The scripts therefore close the project and open it again after `auto_construct_job_project` (`close_project`, `open_project -project <workdir>/job/PolarfireProg/PolarfireProg.pro`) and scan then; that works with 2026.1 and with 2024.2. `auto_construct_job_project` scans the chain itself (`Construct Chain...`, `Scan Chain PASSED`) but prints no device information, which is why the explicit `scan_chain_prg` stays. The stand-in for FPExpress fails a scan without the reopening, as 2026.1 did.
- **Output and crashes:** FPExpress runs on a pseudo-terminal, not a pipe, so that what it printed before a crash is not lost in a buffer (a run on a board printed nothing before a segmentation fault). A signal is named, also as the `128 + N` that the shell wrapper of the snap reports (`139` is signal 11, `SIGSEGV`), and `program.log` has the duration of each run. **A script must not call the Tcl command `exit`:** FlashPro Express 2024.2.0.13 (the snap) crashed with a segmentation fault on it, after a failed action and after a successful `DEVICE_INFO`. The scripts of this command end with `run_selected_actions`; FlashPro Express ends such a script with `The Execute Script command succeeded.` and status 0, or, if a command failed, with `The Execute Script command failed.` and status 1.
- **Exit status:** 0 done (or `--dry-run`), 1 not confirmed, FlashPro Express failed (status other than 0), printed nothing, or did not print `The Execute Script command succeeded`, or a scanned chain shows no device, 2 a set-up error, 130 after Ctrl+C. `run_selected_actions` returns an empty value on success, so no return value is evaluated. FlashPro Express prints `Executing action <ACTION>` when the action starts: if it failed before that (the check of the chain against the file), the message says nothing was written; a read-only action says so too.
- **A file for another device:** FlashPro Express warns `The programming file '<file>' is for 'MPF300TS_ES' devices. Your current device 'MPFS250(T_ES|TS_ES)' doesn't match the programming file.`, changes the device to the one of the file and then fails the check of the chain (`Found: MPFS250(T_ES|TS_ES), Expected: MPF300TS_ES`) before the action starts. The command repeats that as `the programming file is for … devices and the chain has …`. A file for an MPFS250, such as `260521-pfsoc_sdio.stp`, gives no warning.
- **Verified:** against a stand-in for FPExpress (`tests/host/hw/run.sh`, `tests/host/hw/fake_fpexpress.py`), which prints the programmer and device lines as they were seen on a board, stops without the job project directory and without a loaded file, fails the check of the chain for a file of another device and crashes on the Tcl `exit`. On an embedded FlashPro6 with an MPFS250 the detection of the programmer and of the device (`--scan`) ran, and `--action DEVICE_INFO` with a file for an MPFS250 ran through (`Executing action DEVICE_INFO PASSED`; the device and its digests were listed); the segmentation faults of the first runs were the `exit` of the script, not the device name. The device name goes to FlashPro Express as the scan prints it (`MPFS250(T_ES|TS_ES)`, which `enable_device` accepted); splitting it into `MPFS250T_ES` was tried and taken out again because it did not work as hoped on the board. **`PROGRAM` with the PPD of the Icicle Kit base design (`MPFS_ICICLE_KIT_BASE_DESIGN.ppd`) ran through on the board** (`Executing action PROGRAM PASSED`, `Chain programming PASSED`, one minute at 4 MHz). That run used the version of the script that still ended with `exit`; later runs of the version without `exit` passed (see `docs/lab/results/p1.md`), one of them with two FlashPros connected and the programmer named by `run_selected_actions -name`. `PROGRAM` from a `.stp` was reported to work, without a log. The clock path ran against a FlashPro5: `configure_flashpro5_prg` succeeded, and FlashPro Express reduced the 30 MHz asked for to 15 MHz because of the chain; `--tck` on a FlashPro6 has not been reported.
- A `.stp` and a `.ppd` are the file types that were used; another file is tried with a warning. A `.job` file, which FlashPro Express and Libero SoC use, is not supported by this command.
