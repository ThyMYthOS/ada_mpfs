# Configuration management

How the repository is managed today: what is a configuration item, how a change gets in, which files
are generated and how the checks reproduce them, what the CI checks, how the tools are pinned, how
licences and provenance are recorded, and how a change is reviewed. Each statement names the file it
comes from. What the repository does not decide yet is collected under [Open decisions](#open-decisions);
nothing there is a rule.

## Configuration items

- The configuration items are the files that git tracks in this repository (`git ls-files`). The
  version of a configuration is a git commit; the repository has no release number and no tag
  (see [Open decisions](#open-decisions)).
- Build products are not tracked: `.gitignore` excludes `obj*/`, `build/`, objects, `*.elf`, `*.map` and
  similar.
- The merged SVD is generated and not tracked either; the repository records its SHA-256 in
  `svd/PolarfireSoC.sha256` (`svd/README.md`).
- Tools are not tracked. They are identified by the pins in `tools/toolchain.env` and
  `tools/requirements.txt` ([tools.md](tools.md)).

## Branches and pull requests

- `main` is protected: no direct pushes, and pull requests need a green CI (`CONTRIBUTING.md`).
  The protection itself is a setting of the hosting service; this repository holds no file that
  configures it.
- Work happens on topic branches. The workflows run on a push to any branch and again on a pull request
  against `main`, on the merge result; a pull request against another branch shows the checks of
  its head commit; a newer push to a branch cancels the run in progress
  (`.github/workflows/README.md`). The repository states no rule for the names of branches.
- A pull request describes the change and its reason and carries a checklist
  (`.github/pull_request_template.md`, see "How a change is reviewed").
- A change to the pinned tool versions is a pull request of its own, together with re-blessed metrics
  (`tools/toolchain.env`, header); so is a change to `tools/requirements.txt`.
- A rewrite of the analyzer baselines is a commit of its own (`docs/coding-standard.md`).

## Commits

- The prefix follows Conventional Commits: `feat(hal):`, `fix(rts):`, `docs:`, `build:`, `ci:` ...
  (`CONTRIBUTING.md`). The history uses the area as the prefix without a type: `svd:`, `toolchain:`,
  `tests:`, `hw:`, `tools:`, `ci:`, `pac:`, `x:`, `qemu:`, `examples:`, `docs:`, `metrics:`, `renode:`
  (`git log`).
- One logical change per commit; the body says what changed and why (the practice of the history, not a
  rule of a file).
- Every commit carries `Signed-off-by` (`CONTRIBUTING.md`, `.github/pull_request_template.md`). A commit that
  was prepared with a co-author carries a `Co-Authored-By:` trailer, and the author adds the
  `Signed-off-by:` line after reviewing it. No check in the repository or in a workflow tests for the line:
  63 of the 96 commits of the history examined for this document carry one (`git log --format=%B`).
- Commits on `main` are signed (`CONTRIBUTING.md`). The repository holds no list of the keys and no
  check of the signatures (see [Open decisions](#open-decisions)).
- The workflow `pac-regenerate.yml` commits with `git commit -s` as `github-actions[bot]` to the branch of
  a pull request (see below).
- All repository content, commit messages included, is English (`CONTRIBUTING.md`).

## Generated files and the checks that reproduce them

Generated files are never edited by hand; they live in dedicated `generated/` directories or carry a
header that says so (`CONTRIBUTING.md`).

| File | Generated by | Check that reproduces it | Where the check runs |
|---|---|---|---|
| The merged SVD `build/svd/PolarfireSoC.svd` (not tracked) and its hash `svd/PolarfireSoC.sha256` | `./x svd merge` (svdtools over `svd/base`, `svd/patches`, `svd/additions`; validated against `svd/schema/CMSIS-SVD.xsd` with xmllint) | `./x svd check`: rebuilds the SVD, fails on a rule violation or when its SHA-256 differs from the recorded one (`tools/svd.py`) | Job `svd` of `svd.yml` |
| `libs/mpfs_pac/src/generated/` (the register package) | `./x pac generate` (svd2ada at the pinned commit, then `tools/pac_gen.py`) | `./x pac check`: regenerates into a temporary directory and fails on any difference with the committed files, checks that every hand-written source is listed with the strict switches in `mpfs_pac.gpr`, and compiles the package for the E51 and the U54 ABI (`tools/pac.sh`). The header of each generated file names the SVD hash and the svd2ada commit. | Job `pac` of `pac.yml` |
| `metrics.golden` | `./x metrics bless` | `./x metrics verify`: size, entry point, `e_flags` and `Tag_RISCV_arch` of every built image against the file; the file is committed together with the change that caused the difference (`metrics.golden`, header) | Job `build` of `bare.yml` |
| `docs/assurance/trace-matrix.md` | `./x trace` | `./x trace --check` | Job `trace` of `hygiene.yml` |
| The version table of `docs/assurance/tools.md` | `./x tools-doc` | `./x tools-doc --check` | Job `trace` of `hygiene.yml` |
| `tools/analyzer-baselines/` | `./x analyze --update-baseline` (with and without `--style`) | `./x analyze` and `./x analyze --style` report only what is not in the baselines | Job `analyze` of `analyze.yml`, only when baseline files exist (none are committed yet) |

`pac-regenerate.yml` regenerates the register package with the pinned svd2ada and commits the result
to the branch of the pull request. It runs on request (`workflow_dispatch`) and when the workflow file
itself changes, and it needs a branch of this repository: a pull request from a fork gets a read-only
token. It is for changes of the SVD where svd2ada is not available to the author.

## What the CI checks

All logic is in `./x` and the tools; a workflow installs, caches and calls (`.github/workflows/README.md`).
The workflows have `contents: read` permission, except `pac-regenerate.yml` (`contents: write`).

| Workflow, job | Runs on | Checks |
|---|---|---|
| `hygiene.yml`, `reuse` | Every push to any branch and every pull request against `main` (no path filter) | `reuse lint` (reuse 6.2.0) and `tools/headers.py check`: SPDX headers, and a `PROVENANCE.md` entry for every file with a `Derived from` header |
| `hygiene.yml`, `trace` | As above | `tools/trace.py --check` (every `@req` and `@verifies` reference resolves, every TSF requirement has a test, the matrix is current), `tools/tools_table.py --check` (the table of pinned versions is current and every pinned tool has a row), and the host suites of both tools |
| `svd.yml`, `svd` | Push and pull request, for the paths of the SVD, its tools and the host tests | `./x svd check`, `tests/host/svd/run.sh`, `tests/host/x/run.sh` |
| `pac.yml`, `pac` | Push and pull request, for the paths of the SVD, the PAC, its tools and the host tests | `tests/host/pac/run.sh`, `./x pac check` |
| `bare.yml`, `build` | Push and pull request, for the paths of the examples, `hw/`, tests, tools, `metrics.golden` and `x` | `./x test examples`, `./x metrics verify`, `./x test negative` and the host suites `bare`, `report`, `negative`, `qemu_tests`, `stack`, `hw`, `analyze`, `prove` (the cases with stand-ins) |
| `bare.yml`, `qemu` | As above | `./x test qemu`: the smoke test and the `Test_Report` applications |
| `bare.yml`, `renode` | As above | `./x test renode`; "not required for a merge" (`.github/workflows/README.md`) |
| `quality.yml`, `prove` | Push and pull request, for the proof projects, `tools/prove.*`, the pins, `libs/` and `x` | `./x prove` and `tests/host/prove/run.sh` with the real gnatprove |
| `analyze.yml`, `analyze` | Push and pull request, for the paths of the analysis; only when `tools/analyzer-baselines/*.baseline` exist | `./x analyze`, `./x analyze --style` |
| `analyze.yml`, `baseline` | By hand, with "Write the baselines" | Writes the baselines and uploads them as the artifact `analyzer-baselines` (retention 14 days) |
| `pac-regenerate.yml`, `regenerate` | By hand, and when the workflow file changes | See above |

A workflow with a path filter does not report for a change outside its paths, so a status must not be
required for merging unless the workflow has no filter; only `hygiene.yml` has none
(`.github/workflows/README.md`). Which checks are required is a setting of the hosting service and is
not in the repository.

The tools fail closed: a missing tool, another version, an empty input or an output that is not the
tool's own is a failure, not a pass (`docs/coding-standard.md`, "Shell and Python tools"); every such
rule has a test with a control case (`docs/coding-standard.md`).

## The pinned toolchain

- All tool versions are in `tools/toolchain.env`, the Python packages in `tools/requirements.txt`
  ([tools.md](tools.md) lists them). `tools/mpfs-env.sh` puts exactly the pinned versions on `PATH`
  and reports a missing or different version as an error, unlike a "newest wins" lookup.
  `./x toolchain check` reports every deviation.
- The CI caches the toolchains by `hashFiles('tools/toolchain.env')`, so a change of a pin is a new
  cache.
- Downloads are checked against a SHA-256 in `tools/toolchain.env` before they are used: the Alire
  release binary (`alr`, three platforms), the svdtools release binary (three platforms) and the
  Renode release (x86_64 Linux) (`x`, `mpfs_install_alr`, `mpfs_install_svdtools_binary`,
  `mpfs_install_renode`). A failed check removes the download and fails the install.
- svd2ada is built from source at a pinned commit; the install fails if `HEAD` of the clone is not that commit
  (`x`, `mpfs_install_svd2ada`), and `./x pac generate` refuses an svd2ada that is not the pinned build
  (`tools/pac.sh`).
- The Alire crates (GNAT, gprbuild, gnatprove, adalang_analyzer) are pinned by version. The repository
  records no checksum for them. The Python packages are pinned by version without hashes
  (`tools/requirements.txt`). The actions of the workflows are pinned by version tag
  (`.github/workflows/README.md`), not by commit.
- QEMU and the Python interpreter are provided by the operating system and checked against a minimum.
  The OpenOCD of SoftConsole is not checked ([tools.md](tools.md)).

## Licences and provenance

- Every non-trivial file carries an SPDX header (`SPDX-FileCopyrightText`, `SPDX-License-Identifier`).
  Code is Apache-2.0, documentation CC-BY-4.0, the SVD and the register package generated from it
  CC-BY-4.0; copied files keep their own licence; the runtime `crates/mpfs_rts` is GPL-3.0-or-later
  WITH GCC-exception-3.1; SPARKNaCl is BSD-3-Clause (`CONTRIBUTING.md`).
- Files that cannot carry a header, and trivial files (short READMEs, templates, configuration),
  are annotated in `REUSE.toml`; trivial files are CC0-1.0 with no copyright claimed.
- `reuse lint` and `python3 tools/headers.py check` check the headers (`fix` adds the default header);
  both run in the job `reuse`. `tools/headers.py` also fails on a file with a `Derived from` header
  that is not covered by `PROVENANCE.md`.
- An imported file carries a provenance note (`Derived from <repository> <path> @ <commit> (<licence>);
  modified for PolarFire SoC.`) and an entry in `PROVENANCE.md`: file, source (repository, commit,
  path), licence, kind (`unchanged`, `adapted`, `new`) and date. The licence texts are in `LICENSES/`;
  `NOTICE` reproduces the notice of the upstream project and the attribution of the SVD.
- "No binary blobs" is a rule of the security-critical set, checked with `tools/headers.py check` and
  `PROVENANCE.md` (`docs/coding-standard.md`).

## How a change is reviewed

- The repository names one code owner for every path (`.github/CODEOWNERS`: `* @ThyMYthOS`). Whether
  the hosting service requires the owner's review before a merge is a setting that this repository
  does not hold.
- The pull request template asks the author to confirm that the `./x` checks pass locally, that the SPDX headers
  are present and `reuse lint` is green, that imported files have a provenance note and an entry in
  `PROVENANCE.md`, that generated files were not edited by hand, and that the commits carry
  `Signed-off-by` and a Conventional Commits prefix.
- The rules of `docs/coding-standard.md` marked *review* have no tool behind them and are checked in
  code review; the other rules name the check that enforces them.
- In the security-critical set every requirement is referenced with `@req` in the spec and with
  `@verifies` in a test, which `./x trace --check` verifies (`docs/coding-standard.md`).
- Issues are reported with the templates in `.github/ISSUE_TEMPLATE/`. Vulnerabilities are not reported as
  issues but by e-mail to the address in `SECURITY.md`; that file says nothing about what happens next.

## Open decisions

The repository does not decide the following. Each item lists the options and a recommendation; none of
it is in force until it is decided and written into the files named above.

1. **Releases and their numbering.** No tag or release exists in the repository, so the only identifier
   of a configuration is a commit. Options: (a) semantic versions `vMAJOR.MINOR.PATCH` as annotated
   tags on `main`; (b) calendar versions; (c) no release, the commit hash identifies the version.
   Recommendation: (a), with a tag for every configuration that is evaluated or delivered, the tag
   signed (see 2), and one place in the sources that carries the version so that an image can report
   it.
2. **Signed commits and tags on `main`.** `CONTRIBUTING.md` says commits on `main` are signed, but the
   repository neither names the keys nor checks the signatures, and the merge method decides who signs
   (a squash or merge commit made by the hosting service is signed by the service, not by the author).
   Options: (a) require signed commits through the protection of `main` and keep an allowed-signers file
   in the repository; (b) sign only the release tags; (c) no signatures. Recommendation: (a) and (b),
   with SSH signing, the allowed-signers file under version control, and a merge method that keeps the
   author's signed commits (rebase or a merge commit, not squash).
3. **Who may merge.** There is one code owner for everything (`.github/CODEOWNERS`). Options: (a) the
   owner merges, with a green CI as the only gate; (b) review by a code owner is required, with
   separate owners for the security-critical set (boot chain, machine-mode cores, cryptography, generated
   configuration); (c) two reviewers for the security-critical set. Recommendation: (b) now, written into
   `CODEOWNERS` and into the protection of `main`; (c) when a second maintainer exists. The author of a
   change does not approve it.
4. **Which checks are required for a merge.** Only `hygiene.yml` has no path filter and can be a required
   status (`.github/workflows/README.md`). Options: (a) require `hygiene` only; (b) remove the path
   filters; (c) add one job without a filter that waits for the filtered workflows and report only that
   one. Recommendation: (c), so that every pull request reports the same required status and a skipped
   workflow cannot be mistaken for a pass; `renode` stays optional.
5. **The `Signed-off-by` rule.** The rule is in `CONTRIBUTING.md` and the pull request template, but nothing
   checks it, and 63 of 96 commits have the line (see "Commits"). Options: (a) a check in the pull request
   workflow that fails on a commit without `Signed-off-by`; (b) review only; (c) drop the rule.
   Recommendation: (a), after the author has added the line to the open branches; a commit made by a
   workflow (`pac-regenerate.yml`) is signed off by the bot identity, so decide with it whether the
   human's sign-off is added at merge or whether bot commits are allowed on `main` at all.
6. **Handling of a security fix.** `SECURITY.md` says where to report and nothing about triage, a private
   fix, disclosure or what is released. Options: (a) fix in public like any change; (b) a private advisory
   and a private branch, the fix merged and released together with the advisory; (c) a private fix with
   a fixed disclosure period. Recommendation: (b), with an answer time for the report, a patch release
   (see 1) and a note in the release that names the fixed commits; write it into `SECURITY.md`.
7. **Retention of CI artifacts and evidence.** The only artifact of the workflows is `analyzer-baselines`
   with a retention of 14 days; the repository sets nothing for the logs of the runs. A later evaluation
   needs the evidence of a configuration to exist when it is asked for. Options: (a) rely on the
   retention of the hosting service; (b) attach the logs and the reports (build, metrics, proofs,
   `./x toolchain check`) of the release configuration to the release; (c) keep them in a separate
   archive repository. Recommendation: (b), attached to the tag of 1, with the SHA-256 of each file,
   and a retention for pull request artifacts of a few weeks.
8. **Pins of the supply chain.** Actions are pinned by tag, Python packages by version without hashes,
   Alire crates by version without a checksum. Options: (a) leave it; (b) pin the actions by commit and
   install the packages with hashes (`--require-hashes`); (c) in addition mirror or record the digest of
   every Alire crate. Recommendation: (b) now, (c) once the evaluation scope names the crates that are
   part of the evidence.
9. **The scope of the configuration list.** The configuration items are all tracked files. Which of them
   are the TOE, which are tools and which are evidence is not written down. Options: (a) keep
   "all tracked files"; (b) a list of the TOE units kept next to the requirement catalogue (the TSF flag
   of `docs/requirements/` already marks the security-critical set). Recommendation: (b), generated
   from the catalogue and the `@req` markers so that it cannot drift.
10. **The vocabulary of commit prefixes and the names of branches.** `CONTRIBUTING.md` names the
    Conventional Commits types, the history uses area prefixes, and no rule exists for branch names.
    Options: (a) keep both as they are; (b) one list of allowed prefixes in `CONTRIBUTING.md`, checked
    in the pull request workflow, and branch names `<area>/<topic>`. Recommendation: (b), because the
    prefix is what a reader of `git log` uses to find the change of an area.
